## Abstract

In decentralized blockchain ecosystems, significant capital transfers by institutional holders, market makers, and large private wallets—colloquially termed "whales"—exert disproportionate influence over token velocity, decentralized exchange (DEX) liquidity depth, and overall network sentiment. Traditional block explorers often provide fragmented raw event logs or attach ungrounded, arbitrary labels to addresses without clarifying the underlying volume threshold, token decimals, or analytical boundaries.

**BOT WhaleTrace** introduces an open, transparent, and verifiable large-transfer analysis system engineered specifically for BOT Chain. The protocol combines:
1. High-speed multi-range RPC transaction and event scanning.
2. Decimal-normalized threshold filtering for both native BOT transfers and ERC-20 tokens.
3. A formal smart contract registry (`BOTWhaleTrace.sol`) on BOT Chain Testnet for immutable on-chain analysis requests and cryptographic report anchoring.
4. A flat, high-contrast, utilitarian analytical dashboard designed without misleading gradients or glossy textures to ensure cognitive clarity.

## 2. Theoretical Framework & Thresholding Model

### 2.1 The Problem with Arbitrary Labeling
Conventional blockchain analytics platforms frequently flag addresses as "whales" using opaque, non-standardized criteria. This leads to false alarms when analyzing high-supply or low-decimal tokens (e.g., 6-decimal stablecoins vs. 18-decimal utility tokens).

### 2.2 Parameterized Threshold Formulation
BOT WhaleTrace enforces an explicit, parameterized threshold equation:

$$\text{Transfer qualifies as Whale} \iff V_{\text{raw}} \ge M \cdot 10^D$$

Where:
- $V_{\text{raw}}$: Raw transfer value extracted from transaction execution payload or log topics (`uint256`).
- $M$: User-defined or protocol-stipulated minimum human-readable threshold (e.g., $10,000\text{ BOT}$).
- $D$: Authentic token decimals, fetched dynamically via ERC-20 `decimals()` (or $D = 18$ for native BOT).

Every analysis generated by the engine outputs an explicit `thresholdExplanation` string, establishing a transparent audit trail for the criteria applied.

### 2.3 Volume Concentration & Role Identification
To accurately identify the dominant liquidity actors within a scanned block window $[B_{\text{from}}, B_{\text{to}}]$:

- **Top Sender ($S^*$):**
  $$S^* = \arg\max_{A} \sum_{t \in T,\, \text{from}(t) = A} V(t)$$

- **Top Recipient ($R^*$):**
  $$R^* = \arg\max_{A} \sum_{t \in T,\, \text{to}(t) = A} V(t)$$

- **Two-Way Whale:** Any address $A$ where $\text{SentCount}(A) > 0$ and $\text{ReceivedCount}(A) > 0$ with total volume exceeding the cumulative threshold percentile.

### 3.1 Native BOT Block Scanner
For native BOT transfers, the engine parses full block objects across the requested range $[B_{\text{from}}, B_{\text{to}}]$:
- Filters for `tx.value >= parseUnits(M, 18)`.
- If an optional wallet address filter $W$ is specified, checks $\text{from}(tx) = W \lor \text{to}(tx) = W$.
- Records transaction hash, block number, timestamp, sender, and recipient.

### 3.2 ERC-20 Transfer Log Filter
For token contracts, the engine constructs a bloom-filtered log query:
- `address`: Contract address.
- `topics[0]`: `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef` (Keccak-256 of `Transfer(address,address,uint256)`).
- Dynamically resolves contract `decimals()`, `symbol()`, and `name()`.
- Extracts 32-byte padded addresses from topics 1 and 2, and decodes `data` uint256 value.

## 4. Smart Contract Specification: `BOTWhaleTrace.sol`

The smart contract serves as an immutable, trust-minimized verification registry deployed on BOT Chain Testnet at `0x43ce602029F165B2F0349ec060e08dfcd5D9f738`.

### 4.1 Data Structures
```solidity
struct WhaleRequest {
    bytes32 id;             // Unique identifier for the inspection
    address requester;      // Caller submitting the analysis task
    address token;          // Token contract address (address(0) for native BOT)
    uint256 minimumAmount;  // Minimum threshold in raw token base units
    uint256 fromBlock;      // Starting block number
    uint256 toBlock;        // Ending block number
    bytes32 reportHash;     // Cryptographic digest of findings
    bool isResolved;        // Resolution status flag
    uint256 requestedAt;    // Request timestamp
    uint256 resolvedAt;     // Finalization timestamp
}
```

### 4.2 Core Interface

#### `requestWhaleAnalysis`
```solidity
function requestWhaleAnalysis(
    address token,
    uint256 minimumAmount,
    uint256 fromBlock,
    uint256 toBlock
) external returns (bytes32 requestId);
```
- Validates that `toBlock >= fromBlock` and `minimumAmount > 0`.
- Generates a deterministic `requestId`:
  $$\text{requestId} = \text{keccak256}(\text{msg.sender}, \text{token}, \text{minimumAmount}, \text{fromBlock}, \text{toBlock}, \text{block.timestamp}, \text{nonce})$$
- Emits `WhaleAnalysisRequested`.

#### `publishResult`
```solidity
function publishResult(
    bytes32 requestId,
    bytes32 reportHash
) external;
```
- Validates that the request exists and is not yet finalized.
- Anchors the cryptographic report digest (`reportHash`) on-chain.
- Emits `WhaleAnalysisPublished`.

#### `getRequest`
```solidity
function getRequest(bytes32 requestId) external view returns (WhaleRequest memory);
```
- Public view function returning complete parameters, status, and anchored report hash for verification.

## 6. Security & Environmental Considerations

- **Server-Side Environment Security**: Sensitive keys (`PRIVATE_KEY`) and Reown IDs (`REOWN_ID`) are maintained strictly within the server environment and never exposed in client JavaScript bundles.
- **Reentrancy & Overflow Safety**: Implemented on Solidity `^0.8.20` with built-in arithmetic overflow protection and clean state transition guards.
- **Permissionless Verification**: Anyone can verify that an off-chain analysis matches an on-chain anchored report hash by computing:
  $$\text{reportHash} = \text{keccak256}(\text{canonicalAnalysisJSON})$$
